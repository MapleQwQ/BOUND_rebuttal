### Questions

1. **[A.Q1-Architectural Insights]** In RQ2 Finding 4, we observed distinct reasoning styles that can be linked to agent design. AutoCodeRover’s AST/API-guided navigation improves patch stability but can restrict exploration, leading to conservative behavior. TraeAgent’s iterative exploration and test-time scaling increase search breadth, but make boundary control and tool-state stability harder. mini-SWE-Agent’s lightweight bash-centered loop preserves flexible repository exploration while keeping the interaction structure simple. These observations suggest preliminary design principles: repository-level agents should avoid overly narrow search, control redundant exploration, and maintain robust tool-state management. We will revise the paper to present these architectural implications more clearly.
2. **[A.Q2-Implementations Diversity]** We agree that feature addition may have multiple valid implementations. Thus, RACE-bench reasoning metrics measure alignment with developer-accepted reference trajectories rather than absolute correctness. Final test-based correctness is still determined by FTP/PTP tests. Since agents receive FTP tests in the prompt, solutions are constrained by the same expected observable behavior. Following the reviewer’s suggestion, we added a diversity analysis on 100 resolved instances covering 457 successful agent runs. 92.3% of successful runs achieve full Recall@Files and 74.8% achieve full Recall@Tasks, suggesting that most successful patches align well with the reference. For non-perfect cases, GPT-5.5 comparison shows that the most common pattern is `alternative_minimal_path`: the agent satisfies the same feature request through a smaller or different key path than the gold patch. The Astropy case in our case study (https://anonymous.4open.science/r/Race-bench-C35A/case_study.md) illustrates this. We will include this analysis in Section 5.
3. **[B.Q1-Scalability]** The construction process is designed to be scalable rather than manually labeling all instances. All stages can be automated, including candidate PR mining, execution-based filtering, FTP/PTP extraction, patch-driven reasoning extraction, and LLM-assisted auditing. Manual inspection is used for quality control, not as the labeling mechanism. To address benchmark aging, the same pipeline can be rerun on new repositories or newer PRs to periodically regenerate fresh instances. We will release scripts and clarify this scalable reconstruction process.
4. **[C.Q1-Validation Details]** In the replication package (https://anonymous.4open.science/r/Race-bench-C35A/construction/README.md), we have added the full LLM-audit artifacts and the 100-instance manual audit sample for reasoning ground truth construction. We also added a detailed README documenting the prompts used for ground-truth generation, input contexts, GPT-5.2 audit prompt, and manual validation protocol. Additionally, we added a separate human annotation check (https://anonymous.4open.science/r/Race-bench-C35A/evaluation/human_annotations/README.md) for the reasoning evaluation procedure: two authors inspected 100 evaluated agent runs and judged whether the framework’s concept, goal, file, task, and step evaluations were reasonable. Authors agreed with the framework in 97/100 runs.
5. **[C.Q2-Test Visibility]** All FTP tests are exposed to the agent while PTP tests are hidden and used only for final evaluation. We will clarify that RACE-bench targets feature-addition issues accompanied by developer-provided tests. Since feature addition requires a shared behavioral interface for evaluation, existing benchmarks often provide explicit component names or file locations in prompts, bypassing the agent’s file-localization and API/design abilities. Therefore, we provide FTP tests as executable specifications. FTP/PTP tests are selected through the execution-based filtering procedure described in Section 2.2.2. For PTP, we execute all tests in the PR-related test files using pytest and retain tests that pass both before and after applying the Gold Patch. 
6. **[C.Q3-Metric Interpretation]** We will clarify that Specific Tasks and Task Steps diagnose different granularities. Specific Tasks capture entity-level implementation changes (i.e., which functions/methods are added, modified, or deleted). Task Steps abstract these changes into higher-level semantic actions (e.g., introducing new capabilities or reusing existing semantics), and therefore capture planning aspects that may not map to a single entity change. Apply-success means that a generated patch can be cleanly applied to the repository. It is distinct from test success and serves as a prerequisite for running FTP/PTP tests. For metric computation, we do not rely purely on LLM-as-judge. Relevant Files are evaluated deterministically. Specific Tasks use exact matching for modified/deleted entities and semantic matching only when deterministic matching is insufficient. Task Steps are first filtered by step type and related tasks before semantic judgment. We have added the exact prompts, model settings, and metric-computation details to the replication package (https://anonymous.4open.science/r/Race-bench-C35A/evaluation/README.md).
7. **[C.Q4-Feature Addition Motivation]** Feature addition differs from bug fixing because bug fixing typically starts from an observed failure, while feature addition requires agents to infer new behavior, design or extend APIs, integrate new capabilities into existing modules, and preserve existing behavior. Thus, the core challenge is not only modifying existing code, but deciding what new behavior should be introduced and how it should be integrated into the repository. This makes feature addition a distinct setting for evaluating agents’ planning and design abilities. Our results support this distinction: agents often understand high-level intent but struggle to translate it into concrete implementation tasks and steps. We will revise the introduction to better motivate this setting.

### Comments

1. **[A.Other-Significance of Problem]** We agree that modern agents can be lightweight and strongly powered by the base LLM (mini-SWE-Agent is a good example). However, our results show that agent architecture still matters. Under the same base model, AutoCodeRover, TraeAgent, and mini-SWE-Agent exhibit clearly different patch-level performance and reasoning styles. This suggests that even when agents expose only a few flexible tools, scaffold design still affects exploration breadth, redundancy control, and tool-state stability. Moreover, RACE-bench does not rely only on explicit textual reasoning traces. For any apply-success patch, we reconstruct Relevant Files, Specific Tasks, and Task Steps from the generated patch using the same patch-driven back-inference procedure used for the reasoning ground truth. Thus, RACE-bench can diagnose implicit reasoning reflected in final code changes, making it useful for both minimal agents and LLMs that do not expose explicit reasoning traces.
2. **[A.Other-Novelty of RACE-bench]** Existing feature-addition benchmarks mainly evaluate final patch correctness, while code-reasoning benchmarks such as CRUXEval focus on short, self-contained functions rather than repository-level agent behavior. RACE-bench fills this gap by combining real repository-level feature-addition tasks with structured intermediate reasoning references and executable verification. This enables a dual-track evaluation of both final patch correctness and reasoning quality. We will revise the related work to make this distinction clearer and add a comparison with feature-addition and reasoning benchmarks.
3. **[A.Other-Test Incompleteness]** We agree that developer tests may be incomplete and cannot prove full semantic correctness for all possible implementations. Following prior repository-level benchmarks such as SWE-bench and FEA-bench, RACE-bench derives executable tests from developer PRs. Unlike prior benchmarks, RACE-bench provides FTP tests in the prompt as a unified interface for the expected feature behavior. Thus, our goal is to evaluate whether agents can solve feature-addition issues accompanied by developer-provided tests. Although these tests may not cover all functional requirements, they still provide a practical basis for evaluating agents’ ability to address feature requests with developer-provided tests. To further examine this threat, we added a GPT-5.5-based check on whether FTP tests cover the corresponding Feature Request. We found that 94.5% of instances (499/528) have FTP tests that fully or partially cover the requested feature, while 5.5% remain underspecified. We will report this analysis in the revision.
4. **[A.Other-Model Usage]** Yes, the LLM-based semantic judgment in Section 2.4 uses DeepSeek, and we will clarify this. We explicitly list the model and prompts used for each component during evaluation in the replication package (https://anonymous.4open.science/r/Race-bench-C35A/evaluation/README.md). Importantly, only semantic components use LLM judgment, modules with concrete evidence use deterministic evaluation.
5. **[B.Other-Significance and Reliability]** The intermediate scores reveal failure patterns invisible to final tests alone. Table 3 shows that successful cases consistently have higher reasoning recall and lower over-prediction than apply-success but test-fail cases, suggesting that reasoning metrics are associated with functional success. We agree that the reasoning ground truth must be reliable, fairly compared, and not treated as the only truth. For ground truth reliability, RACE-bench combines patch-driven analysis, GPT-5.2 auditing, and sampled human validation: two authors manually inspected 100 audited instances. For evaluation fairness, we use deterministic or hybrid semantic matching rather than pure LLM-as judge. We further added a separate human audit of the evaluation procedure: two authors inspected 100 evaluated agent runs and checked whether the framework’s concept, goal, file, task, and step evaluations were reasonable. The authors agreed with the framework in 97/100 runs. Finally, since feature addition may have multiple valid implementations, intermediate reasoning evaluation should be interpreted as alignment with developer-accepted reference trajectories rather than absolute correctness. Final correctness remains determined by FTP/PTP tests.
6. **[B.Other-Nolvelty]** Prior work on intermediate trajectories mainly analyzes generated traces, while repository-level agent benchmarks usually focus on final patch correctness. RACE-bench fills this gap by providing structured intermediate reasoning references for real repository-level feature-addition tasks, together with executable patch verification. We will expand the related work and add a comparison table to clarify this distinction.
7. **[B.Other-Five Reasoning Modules]** The five modules are not arbitrary. They form a minimal diagnostic chain aligned with common software-change workflows followed by human developers: understanding the issue, locating relevant files, identifying code entities, and planning implementation steps. We chose this granularity to balance diagnostic power and reliability. A coarser schema would make it hard to identify where agents fail, while a finer schema would introduce more subjective boundaries and reduce annotation consistency. Each module captures a distinct failure granularity: intent-level misunderstanding, file-level mislocalization, entity-level missing/redundant changes, and plan-level omissions. We will clarify this rationale in the revision.
8. **[B.Other-Model Usage]** DeepSeek is used for semantic annotation and also as one evaluated base model, but RACE-bench is not purely DeepSeek-generated. Many components are derived from non-LLM evidence: Relevant Files are extracted from Gold/Test Patches, Specific Tasks are obtained by static parsing of changed entities. DeepSeek is mainly used for semantic annotations such as task purposes. We further use GPT-5.2 auditing and human validation to check the reasoning ground truth. In addition, we evaluate other base LLMs, including GLM and GPT, on RACE-bench Lite.
9. **[B.Other-LLM-as-Judge and Random Nature]** For modules with concrete answers, we do not use LLM-as-judge. In ground truth construction, Relevant Files are extracted from the Gold Patch, and necessary files are identified by test-driven ablation. Specific Tasks are obtained by statically parsing changed code entities, with LLMs only used to annotate semantic purposes. For Task Steps, we reduce subjectivity by using a fixed closed taxonomy of step types and requiring each step to be grounded in at least one Specific Task. The same principle is used in evaluation. Relevant Files are evaluated deterministically. For Specific Tasks and Task Steps, we use hybrid alignment: deterministic matching is applied when entity names/locations or step types/related tasks match, and semantic matching is used only when structural matching is insufficient. To reduce randomness, all LLM calls use temperature=0, and the reasoning ground truth are further checked by GPT-5.2 auditing and human validation. We also added a separate human audit (https://anonymous.4open.science/r/Race-bench-C35A/evaluation/human_annotations/README.md) of the evaluation procedure: two authors inspected 100 evaluated agent runs and checked whether the framework’s concept, goal, file, task, and step evaluations were reasonable. The authors agreed with the framework in 97/100 runs. In addition, our diversity analysis shows that 92.3% of successful runs achieve full Recall@Files and 74.8% achieve full Recall@Tasks, while most non-perfect cases reflect alternative implementation paths rather than random evaluation inconsistency.
10. **[C.Other-Minor Comments]** Apply-success means that a generated patch can be cleanly applied to the repository. Reasoning recall measures how many reasoning ground truth elements (e.g., relevant files, tasks, or steps) are covered by the agent, reflecting reasoning quality rather than final correctness. By “waterfall-like degradation,” we mean that agents perform well on high-level goal understanding, but their recall decreases as reasoning becomes more concrete, from file localization to specific tasks and finally task steps. We will revise the abstract/introduction and Section 4.2 to clarify these definitions.
