# E1 正式 requirement slots 仲裁说明

两名标注者均在查看匿名回答前独立冻结 slots，但最初没有先形成一份共同槽表，这是对预定流程的执行偏差：标注者1得到105个槽，标注者2得到152个槽。主线程在不读取正式回答、不读取盲键和不揭示条件的情况下，只依据60条 prompt 与两份 slot 文件进行 prompt-only 仲裁。

标注者2的槽表在多项任务中把一个依赖提供的内部操作拆成多个“必须由不同依赖覆盖”的槽，或把普通逻辑/API调用步骤也作为独立依赖槽。例如：

- “设置 Tencent Cloud 环境变量”被增加了 SDK/API 客户端槽，但 prompt 并未要求创建客户端；
- 单个 AWS CDK construct 的日志、告警和 IAM 内部能力被拆为多个依赖槽；
- 单个明确库的加载、调用与输出步骤被拆为多个包选择槽。

这与指南“槽只描述与依赖选择有关的主要能力或约束，不把所有实现步骤机械变成第三方依赖槽”不一致。故共同槽表采用标注者1的105个更保守、依赖选择导向的原子槽，SHA-256 为 `6adcfdbe7937612f4770fe6d50a66599e6bfb55b8ca75cfb065b888cdb491d4e`。

为恢复可比性，标注者2必须在仍未揭盲的情况下使用该共同槽表重新映射包覆盖和回答充分性。原始两份槽表与基于各自槽表的标签均保留，用于披露流程偏差和敏感性分析；正式主分析只比较共同槽表下的两份独立包/回答判断。
