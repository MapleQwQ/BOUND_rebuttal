# 旧版草案：全量共同提示池上的 Base–BOUND 对照

> 2026-09-24 用户已将执行方案改为随机抽取1,000条提示，并直接复用历史Base。本文件仅保留设计讨论；当前协议、运行状态和结果以同目录的 `design_and_results.md`、`process_log.md` 为准。

日期：2026-09-24。本文是新增实验设计，不是已完成的结果，也不替代已有 confirmatory-200 的记录。旧 E3 的 200 条结果已经可见，因此本次全量扩展应明确标为 **post-result expansion / full-pool census**，不能包装成未看结果前预注册的独立确认实验。

## 1. 要回答的问题与结论边界

主问题：在同一个未经基模风险阈值筛选、且未进入任何 BOUND 编辑流程的 benchmark 提示池上，三个模型的 Base 与四个 BOUND 编辑版本相比，含不存在包名的回答率发生多少**绝对变化**？这种变化是否伴随空输出、拒答、包数下降或对原本低风险任务的新错误？

实验可以回答“此合成 benchmark 的未筛选 held-out 部分上是否有收益”，不能把它称为真实开发者请求分布。只测包名存在性也不能回答推荐是否适合任务、能否安装或代码能否执行；这些须由嵌套语义审计或 E1/E4/E8 补充。

## 2. 冻结全量 manifest：同时报告三个分母

现有来源 `LLM_LY.json` 共 4,892 条记录；既有排除审计记录 918 条与 24 个 `edit_records.jsonl` 的编辑提示重合、13 条池内规范化重复，余下 3,961 条 eligible。以上数量是**待新版运行前复核的现有审计结果**，不能假定 `edit_records` 已涵盖所有 localization、调参和调试提示。

| 分母 | 现有数量 | 用途 |
| --- | ---: | --- |
| 原始记录 | 4,892 | 覆盖检查；允许按原始记录权重展示描述性结果 |
| 规范化去重后提示 | 4,879 | 实际生成任务；每个唯一提示只运行一次，保存原始记录 ID 映射 |
| 全局 held-out、无编辑泄漏的唯一提示 | 当前为 3,961 | **主分析分母**；若补充定位/调参/调试泄漏审计发现新重合，以冻结后的最终数量为准 |
| 编辑重合提示 | 当前为 918 | 单独报告 in-sample 诊断；不并入 held-out 主估计 |

运行前生成 `full_pool_manifest.jsonl`，每行含 `source_id`、原始 prompt、规范化哈希、重复组、各模型/折的 `was_edited`、`was_localized`、`used_for_tuning_or_debugging`、历史风险层、主分析纳入标志和排除原因。按 **所有模型、所有折的泄漏并集**排除，保证三模型使用完全相同的 held-out 任务。保留编辑重合提示并单列，满足“全部 prompt 上跑”的覆盖目标。历史 200 条的成员标志也应写入 manifest。

源码和 manifest 必须复制到项目内的版本化结果目录，保存 SHA-256、构造脚本及逐步排除表；不能只依赖 `/tmp/E3_LLM_LY.json`。使用已冻结的规范化及近重复规则，不根据新结果改变排除阈值。来源包/任务组映射目前缺失，这一泄漏审计限制须披露。

## 3. 生成协议与“原本 Base 结果”的使用

对每个唯一提示、每个模型，运行 **fresh Base + BOUND A/B/C/D**；每个条件生成 5 次。固定与现有 confirmatory-200 相同的 package-recommendation prompt、模型路径、适配器、解码配置（现有脚本默认 `max_new_tokens=64, temperature=0.7, top_k=40, top_p=0.95`）及 `seed=20260926` 的逐 `(prompt_id, replicate_id)` 哈希种子。运行前把实际配置、代码版本和 checkpoint/adapter 哈希写入 manifest。Base 和四折同题、同 replicate seed；同 seed 仅改善配对可比性，不保证文本相同。

按当前去重数，完整运行规模为 `4,879 × 3 × 5 conditions × 5 replicates = 365,925` 条生成，其中主 held-out 分母为 `3,961 × 3 × 5 × 5 = 297,075`。其中 200 条共同提示的 15 个旧条件若逐项核验 prompt 文本、checkpoint、adapter、代码、解码参数、seed 及输出完整性一致，可以直接复用；其余只补缺失记录。复用不是重新抽样。生成结束必须验证每个 `(model, condition, prompt_id, replicate_id)` 唯一且齐全，重复运行基础设施失败时使用原 seed；不得因结果方向重采样。

现存三个 `LLM_LY_response.jsonl` 各有 4,892 个 prompt × 5 次历史 Base 回答。**历史 Base 不作为唯一主对照**：它参与过 high-risk 筛选，与新 BOUND 的时间、代码、随机种子和注册表标签可能不同；而且历史筛选脚本的 `max_new_tokens` 默认值为 **128**，当前 E3 生成脚本默认值为 **64**。主比较使用上述 fresh Base。历史 Base 用于预先定义风险层，以及单独的“复现原始 Base”敏感性表：同 prompt、同冻结标签重算历史与 fresh Base 的差异，解释版本/采样漂移。不得把历史筛选输出与 fresh BOUND 混成声称同 seed 配对的结果。

已有 confirmatory-200 是全量 held-out 的子集且结果已可见。主全量表保留全部 held-out 数据，并额外给出“剔除这 200 条后的新增任务”敏感性表。由于扩样决定发生在观察 200 条结果之后，区间应解释为描述性不确定性，不能称为独立 confirmatory p 值。

## 4. 标签口径与数据质量

原始回答与抽取的包名先落盘；包名抽取、规范化、标准库识别和注册表查询各自版本化，不能只保存最终 `hallucinated` 布尔值。至少提供两种分表：

1. **共同评估日口径（主跨模型比较）**：使用同一个冻结的 PyPI 项目索引。指标名称写成“snapshot 中未列名”，除非独立核实，不把未列名直接称为“从未存在”。保存索引日期、来源、数量、哈希；与 E2new 官方 Simple 索引口径是否一致需运行前核验。
2. **模型 cutoff 口径（原论文可比性）**：核实每个模型实际使用的日期及包首发时间。把 `pre-cutoff exists`、`post-cutoff exists`、`not listed`、`query unknown`、`ambiguous/import name` 分开。E7 尚未完成时，不将旧自动标签误称为已审计的真实时间真值。

两个口径使用同一批原文回答，不重新生成。注册表未知、查询失败、重命名、namespace 或 import/distribution 歧义均记录数量和对主要结论的最好/最坏情形敏感性，不静默并入不存在类。

## 5. 终点、统计和必要副作用

**主终点**：held-out 唯一提示上，回答级未列名事件率 `Δ = mean_f(Sample-HR_BOUND,f) − Sample-HR_Base`；`Δ < 0` 表示改善。分别展示三个模型、四折和三模型等权 macro。报告 Base/BOUND 率、差值百分点、每千条生成事件变化、相对变化（仅在 Base 分母非零时）以及配对 95% 区间。每折独立列出，不能挑最好一折。

**同时报告的质量护栏**：无可抽取包率、逐字空回答率、明确拒答率、平均候选包数、至少一个 snapshot 内包的回答比例，以及回答级 `clean→error` / `error→clean` 四格转移。`无可抽取包` 不等于拒答。包级未列名比例和每千回答未列名包 mention 数为次要终点；比率每次重采样重新按分子/分母计算。另报 top-1/top-5 包名集中度，观察是否退化为常见通用包。任何“减少幻觉”的表述须与这些护栏并列。

历史 Base 五次生成仅定义 `clean (=0/5)`、`low (=1–2/5)`、`high (=3–5/5)` 风险层；新 Base/BOUND 五次只负责估计效果，避免同一批 Base 既定义层又评价回归。在历史 clean 层报告新 Base 基准率、BOUND 新错误率、同 seed `Base clean→BOUND error` 比例和无包变化；不能把历史 clean 等同于“原本任务正确”。

全量唯一提示是固定 benchmark 的 census：对这一有限池，其算术差值不含抽样误差。为了讨论类似任务组成的不确定性，可按 prompt 聚类 bootstrap（建议 10,000 次），同一 prompt 下保留三个模型、Base、四折和五次生成的整体配对；报告 95% 区间，并说明它**不覆盖**编辑集/训练 seed、不同 benchmark 或真实开发者流量的不确定性。折间差异作为独立稳定性信息展示，不把四折 × 五次当作独立 prompt。另做原始 4,892 条记录加权表与 4,879 唯一提示表，检查 13 条重复的影响。

若运行中必须分批查看进度，只查看数量、缺失、失败和耗时，不查看效果方向；停止条件是冻结 manifest 的所有条件/replicate 完成，不能按显著性提前停。若最终发现配置或标签版本不一致，保留旧结果，重新标为敏感性而非覆盖。

## 6. 为充分回应审稿人需要的嵌套补证

全量自动 E3 最直接回应 A/C 的高风险筛选、绝对收益、共同提示集、原本 clean 提示上的回归和统计单位。它**不会**单独回答 B 的 `requests` 退化反例或 C 的任务正确性问题。为此，在查看全量结果前，从 held-out manifest 简单随机冻结一个语义审计子集（建议至少 200 个共同提示；最终数量由标注预算先定，不能依据效果选题）。对 Base 与 BOUND 四折的同一预定 replicate 做盲化双人标注，先冻结任务需求槽，再标核心/可选/无关包、回答 Adequacy、槽覆盖、空输出/拒答；冲突仲裁并报告一致性。三个模型 × 五条件 × 200 提示 × 一次生成需要 3,000 条回答、双人约 6,000 次标注，算力之外的人工成本应提前确认。若预算不足，应预先缩小子集或固定一个折做主语义比较，其余折为敏感性；不能事后选有利折。E1 的 high-risk 标签可作补充，但不能代替该未筛选概率样本。

没有逐提示来源包真值时不要称槽覆盖为“dependency recall”；若来源映射恢复，再单独报告 source-package hit，并说明一个来源包并非全部合理依赖。真实项目、长尾包、安装/import/API/执行及真实 agent/verifier 的问题仍属 E8/E4/E2 范围，不能因全量 E3 已跑而声称全部解决。

## 7. 交付物与验收

- `full_pool_manifest.jsonl`、原始 ID→唯一 prompt 映射、source/checkpoint/adapter/config/registry 哈希、逐步泄漏排除审计；
- 15 个条件的原始逐回答记录（可断点续跑）、完整性 QA 和历史 Base/fresh Base 对照；
- 双 registry 标签、三模型四折主表、原始池/held-out/编辑重合分层表、旧 200 剔除敏感性表；
- 历史风险层与 clean 回归表、质量护栏、prompt-cluster 区间和复算脚本；
- 若实施嵌套审计：抽样 manifest、盲标/仲裁记录、Adequacy 与槽覆盖结果。

验收时须直接写明：held-out 上每千回答减少或增加多少未列名事件，三模型/四折是否同向，空回答及推荐充分性是否变差，以及哪些审稿问题仍没有被此次实验覆盖。允许负结果；不得把全量运行本身视为 BOUND 有效的证据。
